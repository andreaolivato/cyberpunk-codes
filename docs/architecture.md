# Architecture & decisions record

Living document. Every decision that future work needs to respect or knowingly revisit.
Last full update: 2026-08-14 (docs-vs-code audit, after gig 01 played through clean).

## Repository

- **Monorepo** (`Cyberpunk.Codes`), one folder per gig under `mods/`, shared code
  in `shared/`, tooling in `tools/`. Release tags planned per mod:
  `gig-01/v1.0.0`. Releases = zips mirroring the game folder, built by script.
- **`tools/questkit/` is the toolkit, `tools/gen_*.py` is the gig** (split
  2026-08-16). The builders (`scene.py`, `questgraph.py`, `journal.py`) hold
  engine shape and take a `configure(...)` call for one mod's paths and naming;
  the generators hold that gig's anchors, tables and dialogue. Gig 02 imports
  the first set and writes only the second.

  **This is a BUILD-TIME toolkit and it is deliberately not a "core mod".**

  In this game a core mod is a runtime component: ArchiveXL is a RED4ext DLL,
  Deceptious Quest Core is a shared activation hook. Each exists to solve a
  runtime capability or conflict problem. Ours is authoring machinery that runs
  on the author's machine, so splitting it costs players nothing.

  Publishing it as a Nexus core mod would add a download, a version to mismatch
  and a permanent compatibility obligation, for no player-visible gain. Revisit
  only if a third party hits a wall a runtime component would fix.

  Any future refactor here is provable the same way this one was: everything the
  game loads is generated, so regenerate and check `git status` is empty. Empty
  means byte-identical output, which means the playtested archive is untouched
  and no rebuild or playtest is owed.
- If the repo sits in a synced folder, keep heavy intermediates gitignored.

## Toolchain (the only viable stack; no alternative "engines" exist)

Roles as SHIPPED, not as planned. The "planned" column this table used to carry
had gone stale in three rows.

| Layer | Role |
|---|---|
| WolvenKit 8.20 (GUI+CLI) | resource authoring: JSON ⇄ CR2W conversion, archive packing |
| ArchiveXL | loads journal / localization / voiceover map / lipmap / streaming / questphase extensions via `.archive.xl` |
| redscript | gameplay logic + UI wraps, ships as source, compiles at game launch |
| TweakXL | database records. In use, `source/tweaks/shard.yaml` |
| Codeware | scripting utilities. In use, `DynamicEntitySystem` spawns the guards, Hoshino and the Mama Welles stand-in |
| CET (Lua) | dev tooling only, never shipped gameplay logic |

**Audioware is NOT a dependency and is not shipped.** It sat in this table for
a long time as "planned for Elena/Hoshino AI voices". That was wrong about the
mechanism.

A scene line resolves BOTH its subtitle and its audio from one
`scnlocLocstringId` RUID, through a mod-supplied `locVoiceoverMap` that
ArchiveXL merges. No script driver, no playback layer, and gender variants
handled natively.

Audioware would only have been needed for scripted captions, and those were all
rebuilt as scenes. Players install nothing extra for the voices.

**Voices are generated with ElevenLabs**, disclosed on the mod page, subtitles
always. See "Voice" below for the mechanism that gets a wav into the game, which
is the part that generalises to any custom audio.

**Authoring model:** all game resources are authored as WolvenKit JSON under
`source/wkit/raw/`, converted + packed by `tools/build-archive.ps1`. No GUI
authoring; everything reproducible from text files in git.

### What is deliberately NOT gated, and it was researched, not skipped

**"Has V met Nix" and "has V met Mama Welles" both have real signals**, found
the same day: `codex_nix` (set in `mq015_01_hook` / `mq016_02_afterlife`, gates
his codex entry in `journal_entries_bugfixing.questphase`) and
`sq018_mama_welles_met` (read by `base\quest\character_entries.questphase` to
unlock hers). Neither is a gate here, because **both belong to optional content
and can legitimately stay `0` for a whole playthrough**, and a gate that can
stay false is a deadlock with no error message, indistinguishable from a broken
install. Both are in the CET dev menu's fact list, read-only in spirit, so a
real save can be inspected before anyone changes their mind.

The generalisable rule, and the one to read this whole file with:

**Gate on the fewest conditions that prevent an actually-nonsensical experience,
not on everything that could be checked.**

"It never started" is the hardest bug report to act on.

### There is no time-of-day condition: DROPPED 2026-08-14, the design call

Built and removed the same day. The rationale for the removal is what should
survive: it was flavour on the one mechanism whose failure mode is invisible.

Its most likely effect in the field was a tester concluding the trigger was
broken, while it was in fact waiting. Do not add it back.

The shape it had, for the record, because it is a good shape in the right place:
prefer 20:00-05:00, but only for 300 s, after which start anyway, and only
accrue that budget once every other condition already holds. A preference with a
cap can delay the gig; it cannot prevent it, which is the whole difference
between a preference and a gate.

## Map pins: SOLVED (native). READ THIS FIRST FOR EVERY NEW GIG.

**The recipe (game 2.31 + Phantom Liberty).** A quest map pin needs THREE
things. It needed a fourth until 2026-08-14; see the correction below.

1. **A `gameJournalQuestMapPin` entry** under the objective in our journal file,
   plus a `gameJournalPointOfInterestMappin` under `points_of_interest/...` for
   the gig icon.
2. **The pin entry must be ACTIVATED by the quest phase.** Activating the quest,
   phase and objective is NOT enough. Pin entries are journal entries with their
   own state, and an Inactive pin is invisible to the engine (it never even
   queries the mappin system). This single omission produced every "pins are
   impossible" symptom below and cost a full day.
3. **The pin must reference a base-game node in an ALWAYS-LOADED sector, with
   the exact vector from that node to the target in its `offset`.**
   `reference.reference` on a quest pin, `staticNodeRef` on the POI. The tables
   are `ANCHOR_POS` and `PIN_POS` in `tools/gen_journal.py`; the generator
   subtracts them, so the anchor's distance from the target is irrelevant.

**The position** then comes from ArchiveXL, which computes
`GetNodeTransform(anchor) + offset` and builds the cooked entry itself. Nothing
is patched into the game's files: **the mod ships 141 files and not one of them
is under `base\`.**

With those three: native pin, correct icon, gig icon, journal km, auto-tracking
and GPS directions, all confirmed in game 2026-08-14 with no base-game override
and no plugin of our own.

### The anchor must never unload

`GetNodeTransform` needs the node to exist as an instance, i.e. its
streaming sector to be loaded. **A quest activates its pins while V is on the
far side of the city.** So an anchor in an ordinary `exterior_*` sector cannot
place a pin the player has not already walked to, which is every pin worth
having.

Night City has exactly three sectors the engine never unloads - 
`always_loaded_0/1/2.streamingsector`, `category: AlwaysLoaded`, float-max
streaming box. Holding 5211 globally-named nodes. Every pin in gig 01 found
one within 53 m. `tools/find_pin_anchors.py` scans exactly these (it used to
scan `exterior_*`, which is the wrong set, and every anchor it recommended
before 2026-08-14 is unusable).

### Three routes that fail, and how to tell them apart from the log

All tried in game on 2026-08-14. The log line tells them apart:

| what you ship | log | meaning |
|---|---|---|
| anchor in an `exterior_*` sector | `Can't resolve ... position` | name resolved, node not streamed in |
| **no** NodeRef, world coords in `offset` | *(no line at all)* | a quest pin with no reference is never spawned as a mappin, so nothing is asked for |
| a marker node we ship | `Can't resolve ... reference` | the name we wrote was not a name. See the correction below |

The middle one is worth dwelling on: ArchiveXL fully supports a null-reference
pin (`position = offset`) and it works for the POI: which resolved and drew
correctly. It does not work for a quest pin, because the engine never asks. Of
4276 vanilla quest map pins, 4176 carry a NodeRef and `offset` is a small local
nudge every time, `(0, 0, 0.5)` in 4151 of them, never a world coordinate.

**"Custom marker nodes never resolve" is TRUE and was wrongly overturned.** This
file spent 2026-08-14 arguing the opposite on the strength of Californication
and OneMoreLight, which ship their own marker nodes in an always-loaded sector.
**playtesting then confirmed their pins are broken in game too.** They were never the
precedent they looked like, and three test sessions were spent on it. The
generalisable rule: *counting uses in a shipped corpus is only evidence if their
case is your case AND the thing you are copying actually works, verify both
before building on it.*

**And the reason given for it was wrong, measured 2026-08-17.** A node a mod
ships DOES register a global name, provided the name is written as a full
`$/03_night_city/#district/area/#node` path. The short `#node` form registers
nothing, and the short form is what this repo wrote everywhere, which is what
produced `Can't resolve ... reference`. `gotchas.md` #34 and `backlog.md` 11
have the probe and its trap.

What survives unchanged is the operational advice: this gig's pins anchor to
base-game nodes, because whether a pin resolves against a long-form name of ours
has still not been tested. What does not survive is "a mod cannot name a node",
which was carried here for months and shaped the pin architecture.

### `cookedMultiData` is a red herring

When the journal km went missing it looked like the per-objective table was the
cause. It is not: the whole game has five `cookedMultiData` entries, three of
them 98-position collectible objectives, and all 73 vanilla street stories show
distance and directions without one. Distance and routing come from the per-pin
`cookedData` that ArchiveXL supplies. A planned test to prove otherwise was
built and thrown away when the count came back as five.

### The cooked tables are NOT needed: ArchiveXL does this itself (2026-08-14)

**This reverses the "`patch_cooked_mappins.py` IS LOAD-BEARING" section that
stood here, which in turn reversed an earlier claim that it was inert. Read
the sequence: the mistake repeated in both directions, and its shape is what
there is to learn from it.**

What ArchiveXL 1.26+ actually does, read from
`src/App/Extensions/Journal/Extension.cpp` and confirmed against the strings in
the installed 1.27.1 DLL:

- `CollectMappin` walks every mod-added journal entry and records each
  `gameJournalQuestMapPin` / `gameJournalPointOfInterestMappin` in `s_mappins`,
  keyed by journal hash, with its NodeRef and offset.
- It hooks `GetMappinData` and `GetPoiData`, saving and restoring **r8/r9 by
  hand**: the same calling-convention trap our own native attempt hit.
- `ResolveMappinPosition` gives the position:
  - **no NodeRef** → `position = offset`, read as an absolute world position
    (and `CollectMappin` then zeroes the entry's own offset so the engine cannot
    apply it a second time. The giveaway that this is what the field is for);
  - **NodeRef** → `ResolveNodeRef`, then
    `GetNodeTransform(...).position + offset`.
  - Failure logs `Can't resolve mappin #N (path) reference` or `... position`
    and produces no pin at all.
- `OnMappinDataLoaded` pre-reserves capacity in the cooked arrays, and only when
  they are non-empty: the same "never grow an unpopulated `DynArray`" rule our
  plugin work found the hard way.

**Why this went unnoticed for so long:** the hook only
does any of that when the base lookup MISSES (`if (!result && ...)`).
Patching our hashes into the cooked tables made the lookup HIT, so ArchiveXL's
resolver never ran. We shipped a 4343-entry replacement of a core game file to
do a job the loader was already offering to do, and the file was what stopped it
being done. The evidence is in `red4ext\plugins\ArchiveXL\*.log`: six sessions,
seven `[Journal]` lines each, all merge lines, **not one
`Cooked mappin ... requested`**.

**How the wrong conclusion was reached, both times.** On 2026-08-11 activation
was added *and* the cooked patch was already in place, pins started working, and
the credit went to the patch. Nobody removed it to check. The confound is the
same one that produced the original "cooked overrides are inert" error, just
pointing the other way: **two changes, one observation, and an attribution
nobody isolated.** Before crediting an ingredient, take it out.

**Diagnostics.** `ArchiveXL.log` now tells you what happened to every pin, by
name, at info level: `Cooked mappin #N (path) resolved to NodeRef #H`,
`... resolved to static offset`, or the two failures above. Read it before
theorising about a missing pin.

**Custom marker nodes as anchors: IN DOUBT, not settled.** This file said they
"never resolve", tested with `worldStaticMarkerNode` and `worldTriggerAreaNode`.
That test dates from the pre-activation era and was never re-run afterwards
. Exactly like the two conclusions already withdrawn above. The counter-evidence
is strong: **Californication ships a `worldTriggerAreaNode` and a
`worldAISpotNode` in its own `base\journal\californication.streamingsector` and
anchors its pins to them by `#name`** (`#nq_cali_tr_cliff`,
`#nq_cali_ws_judy_sit`), with no cooked tables anywhere in the archive.
OneMoreLight does the same. Our own inert sector
(`mod\negative_balance\world\gig01.streamingsector`) is structurally almost
identical to Californication's. Same node type, same `category: Quest`, same
`level`, same nodeData flags, same float-max streaming box, NodeRef carried in
`QuestPrefabRefHash`. The two differences worth trying if this is ever picked
up: ours names the node at world root (`$/03_night_city/#cc_g01_office_marker`)
where Deceptious nests his under an existing base-game prefab chain, and ours
has `sourcePrefabHash: 0` where his is non-zero. **Treat "custom markers never
resolve" as unverified.**

**Dead ends (do not repeat):** the scripted-pin layer that once shipped
here. A `BountyHuntVariant` mappin plus a `CustomPositionVariant` waypoint to
force GPS routing, plus a `Gig01_MappinShim.reds` wrapping the quest-log UI for
distances. Has been deleted. It fought the engine's own routing and is
unnecessary now. Magic numbers, still current (Int32 journal hashes =
Murmur3-32(path, 0x5EEDBA5E)): quest -2069982238, phase_main -1762332001,
obj_office 631112275, obj_epilogue -228359427.

**Level 2 (ATTEMPTED AND CLOSED 2026-08-11, the plugin is NOT needed).**
A full RED4ext plugin was built and taken through six iterations before we found
that the real problem was an unactivated pin entry. It is not shipped and should
not be revived; its source stays in `tools/native/NegativeBalanceMappins` only as
a working RED4ext + MASM scaffold for future native work.

Findings 1, 2 and 4 below are solid engine facts. **Findings 3 and
5 draw conclusions that are now known to be WRONG**, both were measured while
the pin journal entries were Inactive, so the engine had no reason to query
anything. Native pins do work; see the playbook.

1. Injecting into the cooked resources at ArchiveXL's offsets (0x58/0x68) writes
   into EMPTY arrays. Logged `cooked=2` after adding 2 entries, while the engine
   resolved hundreds of base-game hashes fine.
2. Growing an unpopulated RED4ext `DynArray` is FATAL: the allocator pointer is
   stored *after* the entries buffer, so an empty array yields a garbage
   allocator. This caused the repeated flatlines. Only grow populated arrays.
3. The system object IS `gamemappinsMappinSystem` (confirmed via RTTI), and it is
   0x18480 bytes. A full scan of all 99 KB found no cooked mappin table at any
   offset. (Conclusion drawn at the time, "injection is impossible" - was moot:
   injection was never needed).
4. Hooking `GetMappinData`/`GetPoiData` with a C++ detour destabilises the game
   (the callers expect r8/r9 preserved, ArchiveXL saves them by hand). An
   assembly stub that tail-jumps to the original for unknown hashes is stable and
   is the correct technique (`src/Hook.asm`).
5. With that stable interception serving our hashes, the engine never queried
   them (no `[SERVED]` log lines). **The conclusion drawn from this, that the
   engine does not look up mappins for runtime-merged content, and that the
   association is baked at cook time. Was WRONG.** The pin entries were Inactive
   throughout that test, which is why nothing was ever asked for. With them
   activated the engine queries normally and the cooked tables answer.

~~Conclusion: no runtime hook or injection can produce a native quest mappin for
a mod-added journal entry on 2.31.~~

**THAT CONCLUSION IS WITHDRAWN, 2026-08-14. This paragraph is kept only so
nobody acts on it.**

It rests entirely on finding 5, which is marked WRONG four paragraphs above. The
engine "never queried our hashes" because the pin entries were Inactive for the
whole test, so it had no reason to query anything. The same invalid measurement
produced the "cooked overrides are inert" claim corrected on 2026-08-11.

**CLOSED FOR GOOD, 2026-08-14, and the reason is that the plugin already
exists and we already ship it. It is called ArchiveXL.** Reading
`src/App/Extensions/Journal/Extension.cpp` (see the section above) shows psiberx
built precisely this: a hook on `GetMappinData`/`GetPoiData` that serves mod
journal hashes the base tables miss. Every hard-won finding in the list above is
independently confirmed by that code. It saves and restores r8/r9 by hand
(finding 4), and it refuses to grow the cooked arrays while they are empty
(finding 2). The investigation was right about the mechanism and wrong only
about who had to write it.

So do not revive `tools/native/NegativeBalanceMappins`. It is a working RED4ext
+ MASM scaffold and worth keeping for future native work, but the mappin job
is done, by a dependency the mod already requires.

## Device / computer UI: SOLVED (native). See `computer-ui-playbook.md`.

Mod content can be rendered by a base-game computer's own Files/Mails menu, with
no custom widgets. Established 2026-08-11 for gig 01's office ledger
(`Gig01_OfficeComputer.reds`), reusable for every gig.

- The content model is `ComputerControllerPS.m_computerSetup.m_filesStructure`,
  an `array<GenericDataContent>` (folder = `name` + `content: [DataElement]`).
- The only route from the UI to that data is three NON-final PS methods - 
  `RequestFileThumbnailWidgetsUpdate`, `RequestMenuButtonWidgetsUpdate`,
  `RequestMainMenuButtonWidgetsUpdate`. `@wrapMethod` those, top the data up
  before `wrappedMethod`, done. `@addMethod(ComputerControllerPS)` gives helpers
  access to the protected setup.
- Pick out one specific device by its owner's world position
  (`GetOwnerEntityWeak()`), not by record name.
- **Reading a document needs no hook at all**: `OpenDocument` calls
  `ResolveQuestInfo` → `AddFact(game, questInfo.factName, 1)`. Put the fact name
  on the `DataElement`.
- **`AddFact` increments.** Anything reading such a fact must compare `> 0`.
  `gen_questphase.add_pause_fact` already emits Greater-than-0; redscript was
  fixed to match.
- Persistence trap: of `DataElement` only `isEnabled`/`wasRead`/`isEncrypted`
  persist, so a pushed element can come back blank after a reload. The gig's
  implementation repairs the blank in place rather than appending again - 
  see the playbook.

Dead end (do not repeat): guessing the API. `GetFiles`, `OnInstantiated` and
`OnActionEngineering` do not exist on `ComputerControllerPS`; assuming them
broke the whole script bundle. Clone the decompiled scripts and read them.

## Scenes, choices and holocalls: SOLVED. See `scene-playbook.md`.

Established 2026-08-11 (Batch C), **played and confirmed end to end
2026-08-13**. Conversations that need the player to *pick* a line must be
`.scene` resources: choice hubs
are written natively into `UIInteractions.DialogChoiceHubs` and the confirm
press is dispatched back to the owning scene, so a script-injected hub has
nothing to route it to.

- Generated by `tools/gen_scenes.py` into
  `mod\negative_balance\scenes\*.scene`; played by `questSceneNodeDefinition`
  nodes in the quest phase (`gen_questphase.add_scene`). Scenes need no
  `.archive.xl` entry.
- **Scene text lives in the scene's own `locStore`, per locale**: not in our
  ArchiveXL onscreens resource. The only place in this repo where strings are
  not LocKeys.
- **Unvoiced is fine**: line `duration`/`startTime`/`sectionDuration` in
  milliseconds are the pacing, and no bank or lipsync set is required. **Voiced
  is better and costs nothing structural:** a line's `scnlocLocstringId` RUID
  resolves its subtitle AND its `.wem` through a mod-supplied `locVoiceoverMap`,
  natively, with gender variants picked by the engine. Timings then come from
  `durations.json` instead of a character-count estimate. All 54 lines in gig 01
  are voiced this way.
- **A scene line is the ONLY line that can carry audio.** Text pushed from
  redscript is a caption with no RUID, so no voiceover map can reach it. Six
  beats were captions and all six were silent; converting them was the only
  fix.
- **Scene actors cannot be bound to entities we spawn at runtime.**
  `DynamicEntitySpec` has no `uniqueName` (probed with the redscript compiler),
  and community NPCs have no NodeRef discoverable offline. So every non-player
  speaker is a `spawnDespawn` actor the scene spawns for its voice only; the
  visible body is still the encounter script's. Each needs a TweakXL Character
  record purely for the `displayName` over its subtitles.
- **WHERE that voice actor goes decides whether it can be heard** (corrected
  2026-08-13). The old (1000, 1000, -100) offset was invented for subtitles,
  which do not care about position; audio attenuates with distance, so every
  world-emitter line was inaudible. Positional speakers are now buried ~2.5 m
  under the listener or under a fixed anchor near their mark. Straight down is
  preferred: it needs no knowledge of the marker's rotation.
- **Position only matters for `Vo_Expression_Spoken`.** `isHolocallSpeaker` (the
  phone) and `Vo_Expression_InnerDialog` (Johnny, in V's head) are 2D and need no
  anchor at all.
- **Holocall = scene + chrome, meeting at a fact.** Caller lines set
  `isHolocallSpeaker`; the chrome is `PhoneSystem` driven by
  `questTriggerCallRequest` from `Gig01_Holocall.reds`, because the per-contact
  holocall phase vanilla uses does not exist for mod contacts. A mod-added
  journal contact IS a valid call addressee (the phone UI matches on contact
  id). Answering does not raise the call UI. The `StartCall` phase does, and
  an unanswered call times out after 8 s, so ringing must retry.
- **From script the call must be `Audio`. `Video` crashes the game on answer**
  (verified 2026-08-11): Video renders a live feed of the caller, staged in
  vanilla by `questCallContact_NodeType.prefabNodeRef = "#holocalls_studio"`, and
  `questTriggerCallRequest` has no such field. Audio has no render texture and
  still shows the contact portrait. Closed for good 2026-08-13: the only
  route to Video hands the call to vanilla's per-contact phase, which brings that
  contact's own dialogue options with it (`backlog.md` 3d).
- **V DOES speak, through a player actor** (corrected 2026-08-13). The old note
  here said there was none in any scene, and that a player actor would stage V at
  a distant marker. That was inference and it was wrong: `scnPlayerActorDef` has
  **no spawn, marker, offset or position field of any kind**, so it cannot move
  him. It only finds him. Believing otherwise forced every V line to be
  choice-hub text, which is why hub density was four times vanilla's.
- **`sceneLocation` can follow the player.** `scnWorldMarker.type` accepts `Tag`
  with `around_player` (73 uses in shipped street stories, five with no nodeRef
  at all). It does NOT place the marker exactly on V, so use it only where
  position does not matter.
- `sceneLocation` must be a NodeRef that resolves, same rule as map pins, but it
  is only a placement origin. The player can be anywhere, which is what makes a
  fixed anchor usable for a phone call.

## Spoken lines without a .scene: REMOVED 2026-08-13, and do not rebuild it

**This route worked and was still wrong.** It is documented here as a dead end,
not as a technique.

A caption pushed onto the subtitle panel from redscript has no
`scnlocLocstringId`, therefore no RUID, therefore **nothing a voiceover map can
ever key on**. Six beats in gig 01 used it and every one was silent in game. The
fix was not a playback layer. It was to rebuild those beats as `.scene`
resources, which is what shipped.

`ShowSubtitle`, `SpeakAs`, `Line()` and their callbacks are deleted from
`Gig01_Encounter.reds`. They were deliberately not kept as a convenience:
leaving a caption API in the tree invites the next beat to produce a permanently
unvoiceable line. If a beat needs text, write a scene.

`HideSubtitle` survives, because `CCGig01JohnnyLeave` still clears the panel.

Warning banners via `SimpleScreenMessage` remain correct for system/UI feedback
(the ledger download beats), where `type` picks the colour: `Neutral` blue,
`Negative` red, `Connection` netrunner styling.

The mechanism, kept because it is real knowledge about the engine and gigs 02-04
may want a non-dialogue caption:
`BaseSubtitlesGameController` listens on the UIGameData blackboard:

- `ShowDialogLine`: Variant holding `array<scnDialogLineData>`
- `HideDialogLine`: Variant holding `array<CRUID>`

`scnDialogLineData`: `text`, `speakerName`, `type`, `duration`, `speaker`,
`isPersistent`, `id`. Three rules read out of
`cyberpunk/UI/subtitles/baseSubtitlesControllers.swift`:

1. Use `scnDialogLineType.OwnerlessRegular`. It is the only type
   `IsMainDialogLine` accepts without a speaker `GameObject`, so characters
   with no spawned entity (Johnny, Mama Welles) can still talk. `speakerName`
   is just a display string.
2. **Hide before every Show.** A line id sits in `m_pendingShowLines` until it
   is hidden, and a Show whose id is already pending is silently dropped, so
   without the hide only the first line of an exchange ever appears. Sharing one
   default `CRUID` across our lines is fine and even desirable: they reuse a
   single widget, and real scene lines never use that id so our Hide cannot
   remove a game line.
3. `duration` only drives the text-reveal animation. Nothing auto-removes a
   line; hide it explicitly when the exchange ends.

Warning banners remain correct for system/UI feedback (the ledger download
beats), where `SimpleScreenMessage.type` picks the colour: `Neutral` blue,
`Negative` red, `Connection` netrunner styling.

Implementation: removed. See the heading above. The `cc-g01-spk-*` speaker
label keys in `gen_localization.py` are the last trace of it and are now unused;
a scene takes the name from the speaker's Character record `displayName`
instead.

## Toolchain reliability

`tools/check-scripts.ps1` was a no-op from the day it was written until
2026-08-11: `scc -compile <flat temp dir> <cache file>` prints "Compilation
complete" and exits 0 without compiling anything, and so did
`scc -compile <path that does not exist>`. Every "Scripts compile cleanly"
before that date was meaningless, which is how a bundle-breaking change once
passed review. scc only compiles when handed `<root>\r6\scripts` with a sibling
`<root>\r6\cache\final.redscripts`.

The script now:

- builds that layout
- also copies plugin `.reds` that sit loose in the plugin folder rather than in
  a `Scripts` subfolder. mod_settings does this, and missing it produces bogus
  "unresolved reference 'ModSettings'" errors in They_Will_Remember
- treats a missing "Compiling files in" line as failure
- ships `-SelfTest`, which plants a broken file and fails if the check passes

## Voice

Every line in the gig is voiced. The voices are generated with ElevenLabs, which
is disclosed on the mod page, and subtitles are always on.

Two things about the mechanism, which is the part worth copying:

- **Audioware is not a dependency.** A scene line resolves its own audio from
  its RUID through a mod-supplied `locVoiceoverMap`, natively, with no script
  driver behind it. Players install nothing extra to hear the gig. The wav to
  wem step is in `BUILDING.md`; the map is built by `tools/gen_voice.py`.
- **Reusing vanilla takes instead of recording does not scale.** Measured
  against a full index of all 62,992 vanilla spoken lines, exactly 3 of this
  gig's 59 have a verbatim match from the right speaker. Writing dialogue in a
  bark-compatible style and matching it to existing audio afterwards sounds
  workable and is not. Exactly one vanilla take ships, Nix's "How's things, V?",
  which points at vanilla's own `stringId` and so costs nothing.

- **A line that arrives on V's phone is a different asset, not the same asset
  played differently.** The base game ships four processed takes of a voiced
  line, `vo`, `vo_holocall`, `vo_helmet` and `vo_rewinded`, sharing one
  stringId, and ArchiveXL can register only the main map. So the treatment has
  to be baked into the clip a mod ships, which `tools/questkit/phone.py` does
  for the 17 lines Elena and Nix speak on the phone.

  The treatment is not an EQ. Vanilla keeps the line's short-time magnitude
  spectrum and discards its phase, and two builds that fitted the magnitude
  correctly still sounded wrong because of it. `backlog.md` 15 has the
  measurement and both wrong answers; `gotchas.md` 41 and 42 have the parts
  that generalise.

The corpus that measurement came from is `tools/vo_corpus.py`, which indexes
every spoken line in the game and applies well beyond this question.

## Spawning: BUILT, and this is what ships

Codeware `DynamicEntitySystem` from redscript. Quest-graph `questSpawnSet` nodes
only reference existing community spawn phases and are unusable for custom NPCs,
so every NPC this gig places is script-spawned.

| who | record | notes |
|---|---|---|
| Hoshino | `Character.cc_g01_hoshino` | ours, via TweakXL (`source/tweaks/hoshino.yaml`), the one place the "clone an Arasaka record" plan was actually needed |
| guards, netrunners, snipers | ten vanilla `Character.arasaka_*` / `nok_*` / `sts_std_arr_*` records | listed in `Gig01_Encounter.reds`; vanilla records need no TweakXL at all |
| Mama Welles stand-in | `Character.Mama_Welles` | only spawned if the REAL one is absent; the script prefers her |

**Johnny is NOT spawned or placed by script, and nothing searches for him.**
Each of his seven beats is staged entirely by its own scene: the actor is
offset from an `around_player` marker, turned to face V by a computed yaw, made
visible by a workspot, and glitched out by a `scneventsVFXEvent` 250 ms before
the scene ends. One call does all of it, `Scene.stage_johnny`.

That replaced a script route that buried the scene's actor under the floor and
lifted a second body into place, which is where the T-pose, the mid-air
arrivals and the risk of grabbing another mod's Silverhand all came from. See
"STAGING A CHARACTER WHO SPEAKS, LIPSYNCS AND STANDS BESIDE V" in
`docs/scene-playbook.md`, and `docs/backlog.md` 9 for the measurements that
made it possible.

**TweakDBIDs are case-sensitive and are not reliably discoverable from files on
disk.** `Character.Mama_Welles` and her position were found with the CET dev
menu's CAPTURE THE NPC I'M LOOKING AT probe; guessing either fails silently.
